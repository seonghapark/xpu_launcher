### 🐛 Describe the bug

`ProcessGroupXCCL` never overrides `Backend::supportsSplitting()`, so
on XPU it inherits the base default of `false`:

- `torch/csrc/distributed/c10d/Backend.hpp` declares
  `virtual bool supportsSplitting() const { return false; }`
- `torch/csrc/distributed/c10d/ProcessGroupNCCL.hpp` overrides it to
  `return true;`
- `torch/csrc/distributed/c10d/ProcessGroupXCCL.hpp` does **not** override
  it.

Combined with `DeviceMesh._init_one_process_group`'s gate
(`torch/distributed/device_mesh.py:550-562` in torch 2.13), this means
**every nested DeviceMesh creation on XPU under the eager-init pathway
fails**. The gate routes through `dist.split_group(...)`:

```python
# device_mesh.py:550-562
if (
    (
        getattr(default_group, "bound_device_id", None) is not None
        or dist_config.use_torchcomms
    )
    and torch.accelerator.is_available()
    and (
        backend is None
        or default_group._get_backend(
            torch.accelerator.current_accelerator()
        ).name() == backend
    )
):
    dim_group = split_group(...)   # <-- xccl explodes inside here
```

…and `dist.split_group` checks the parent backend's
`supports_splitting` first:

```python
# distributed_c10d.py:5565-5570
if (
    not parent_backend or not parent_backend.supports_splitting
) and not _use_torchcomms_enabled():
    raise RuntimeError(
        "No backend for the parent process group or its backend does not "
        "support splitting"
    )
```

`parent_backend.supports_splitting` returns `False` for xccl, so the
RuntimeError fires before any `xcclCommSplit` is attempted. The gate
itself only checks `bound_device_id` / accelerator availability /
backend-name match — none of those rule out xccl, and xccl's
eager-init pathway always sets `bound_device_id` (you can't disable
it without losing FSDP2's `foreach_all_gather` routing).

### What needs to land

Two parts:

1. **`ProcessGroupXCCL.hpp`** declares a `supportsSplitting() override`
   matching NCCL's:

   ```cpp
   bool supportsSplitting() const override {
     return true;
   }
   ```

2. **`ProcessGroupXCCL::split` (or equivalent)** is implemented and
   exercised by `test/distributed/test_c10d_xccl.py`. Setting
   `supportsSplitting()` to `true` without a working `split()` impl
   just moves the failure from a Python `RuntimeError` to an
   `xcclCommSplit`-shaped C++ crash.

If a real `xcclCommSplit` is not yet feasible, a third option is to
have `ProcessGroupXCCL::split` delegate to `new_group(...)` as a
correctness fallback — same effect as the `new_group` else-branch in
`device_mesh.py`, just delegated from inside the backend rather than
worked around at the Python level.

### Impact in the wild

Without this fix, every `DeviceMesh._unflatten(...)` on XPU raises —
including the EP sparse mesh that `torchtitan/distributed/parallel_dims.py:200-204`
builds unconditionally:

```python
full_sparse_mesh = unflatten_mesh(
    self._world_mesh,
    ("pp", "dp_replicate", "efsdp", "ep"),
    (self.pp, self.dp_replicate, efsdp, self.ep),
)
```

So `moe_2b_ep` (and any future EP / multi-dim mesh config) fails at
trainer init on XPU. Failure surfaces during model build, well before
any forward pass.

### Local workaround

We're currently monkey-patching `DeviceMesh._init_one_process_group`
from a small ezpz-side module
([`xccl_split_group_workaround.py`](https://github.com/saforem2/torchtitan/blob/83e2e8ee0/torchtitan/experiments/ezpz/xccl_split_group_workaround.py))
that:

1. Detects xccl/XPU at module load — no-op on CUDA/CPU builds.
2. On every `_init_one_process_group` call, inspects the parent
   backend's `supports_splitting`. If `True` (NCCL), calls upstream
   verbatim.
3. If `False` (xccl today), temporarily clears `bound_device_id` on
   the default group so the upstream gate's first clause falls through
   to the existing `new_group` loop (the same path xccl already uses
   successfully in single-mesh configs). `bound_device_id` is
   restored in the `finally` so FSDP2's eager-init bookkeeping stays
   intact.

It works — `moe_2b_ep` 2N + `agpt_80b TP=2` 4N both train cleanly
under it on Sunspot. But it's a band-aid we'd like to delete once the
upstream override + `split()` impl land.

  case too (the cpu gloo backend isn't the one raising — it's the
  xpu backend lookup that fires first because of `device_id` binding).
