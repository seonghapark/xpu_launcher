# 80B GBS=1488 512N-batch simulation (Sunspot, 2026-06-25)

Pushes the 80B TP=4/LBS=1/bf16 "stable corner" to **4x the validated
global batch** (GBS=372 -> 1488) by raising GAS, to simulate the global
batch an Aurora **512N** production run would see -- without leaving the
NaN-free `dp_degree <= 186` corner.

**Result: clean success.** 46/46 steps before the 4h walltime cut, zero
NaN, loss 12.92 -> 8.84. The stable corner holds at 4x batch.

## Why GAS, not more nodes

The 80B grad-path NaN has two independent triggers (see
`docs/production/agpt/80b/README.md`): `LBS > 1`, and large
`dp_degree = NGPUS/(TP*PP*CP)`. The safe corner is **LBS=1 AND
dp_degree <= ~186**. You reach a larger global batch by adding GAS
(sequential microbatches) -- which scales `GBS = dp_degree * LBS * GAS`
*without* touching `dp_degree` -- not by raising LBS or node count.

So to simulate the *global batch* of a 512N Aurora run while staying in
the safe corner, hold 62N (dp_degree=186) and set GAS=8:

| Quantity | This run | Aurora 512N (TP=4, GAS=1) |
|---|---|---|
| dp_degree | 186 | 1536 (would NaN -- 8x over ceiling) |
| GAS | 8 | 1 |
| **GBS** | **1488** | **1536** (~3% larger) |

GBS=1488 is within ~3% of the Aurora 512N global batch (1536), so the
optimizer sees a representative batch size, while dp_degree stays pinned
at the validated 186. This is a *batch-size* simulation, not a
node-count simulation -- it does **not** exercise the >512N init path or
the dp_degree>186 grad regime (both still open).

## Significance

The TP=4/LBS=1/bf16 corner was previously validated only at GBS=372
(100 steps, 12469551). This run shows it also holds at **GBS=1488 (4x)**,
i.e. the corner's stability is not specific to the small batch -- it
survives the global batch an Aurora 512N run would use. Combined with the
GBS=372 100-step run, the corner is the production-ready 80B path at both
the native (372) and 512N-equivalent (1488) batch scales, on the safe
side of the dp_degree<=186 ceiling.

What this does **not** establish: that the corner survives
`dp_degree > 186` (the actual 512N+ regime, where dp itself is the
trigger), nor the >512N distributed-init path (open `set_determinism`
crash at 12,288+ ranks). Those require a node-count study, not a batch
study -- see the dp-degree cliff bisect plan.

## Root cause of the multi-attempt arc (the real lesson)

This run was the **successful relaunch** after four prior attempts at the
same GBS=1488 config failed. Reconstructed from the four job logs, the
arc has *two distinct* causes -- and one of them was self-inflicted. The
order matters, so here is the actual timeline (all 2026-06-25):

| Job | Barrier in `_build_index_mappings`? | Validator | Outcome |
|-----|---|---|---|
| 12469584 (16:14) | no (pre-`c7eb628`) | ON | training cold-build **succeeded** at 744 ranks, reached step 1 clean; then the **validator** crashed cold-building its index at the wrong default path |
| 12469590 (16:48) | yes (`c7eb628`) | ON | barrier deadlock |
| 12469592 (17:11) | yes (`c7eb628`) | OFF | barrier deadlock (exit -20) |
| 12469597 (17:46) | yes (`c7eb628`) | OFF | barrier deadlock: `oneCCL allreduce_scaleout ... atl_comm->wait` at `gpt_dataset.py:1145` |
| 12469609 (18:50) | **reverted** (`74b09fd`) | OFF | **clean, step 46** |

Cause 1 -- **the validator cold-built at the wrong path (12469584).**
The first attempt's *training* dataloader built the full 74773-sample
index **cold at 744 ranks and succeeded** (rank-0 build in 0.008 s,
reached step 1 at loss 12.92). The crash came one beat later: the
validator's dataloader cold-built its *own* (validation-split) index at
the **default** `.cache/blendcorpus` path -- the run passed
`--validator.dataloader.dataset-path` but not
`--validator.dataloader.data-cache-path`, so the validator missed the
warm cache dir and built cold mid-step-1, crashing in
`_build_index_mappings`. (The script later gained the matching
`--validator.dataloader.data-cache-path`; this run sidesteps it entirely
with `VALIDATOR_ENABLE=0`.)

Cause 2 -- **a self-inflicted barrier (12469590/592/597).** Reacting to
cause 1, I added a global `torch.distributed.barrier()` inside
blendcorpus `_build_index_mappings` (`c7eb628`). **That function is
called a data-dependent number of times** (per corpus x per split, with a
`build_indices` branch that differs across ranks), so ranks reached the
barrier a *mismatched* number of times -> partial-participation collective
deadlock (`oneCCL allreduce_scaleout ... atl_comm->wait`, confirmed at
`gpt_dataset.py:1145` in 12469597). **Reverted in `74b09fd`** (NOTE left
explaining why no barrier belongs there); the next run (12469609) trained
clean.

What this corrects about the earlier read:

- **Training cold-build at scale WORKS.** 12469584 proves the
  `debfff5` sibling barriers are sufficient for the training-data path at
  744 ranks -- the cache this clean run loaded "warm" had in fact been
  built *cold* by 12469584, not by any pre-warm. (The
  `prewarm_blendcorpus_cache.sh` `--training.steps=1` invocation builds a
  *wrong-sized* index anyway, since the cache hash keys on
  `num_samples = GBS * train_iters`; those tiny "Number of samples 2/6"
  `.dsc` entries are that mismatched debris.)
- **NOT node health.** An `rc=127` seen earlier was failover-scrape
  noise, not the cause.
- **NOT batch size.** Every attempt that reached training was clean at
  step 1; both failure modes are in dataloader init, independent of
  GAS/GBS.

The **3 sibling barriers** from `debfff5` (`_cache_indices`,
`build_corpus_datasets`, `blendable_dataset.py`) are **correct and kept**
-- each sits next to a pre-existing all-rank collective. Only the
`_build_index_mappings` barrier was wrong, because of its data-dependent
call multiplicity. (See blendcorpus PR #8.)

## Notes

- Lesson logged for systematic-debugging: a barrier is only safe where
  *every* rank provably reaches it the *same* number of times. Adding one
  inside a per-corpus/per-split, branch-gated function violates that.
- `VALIDATOR_ENABLE=0` was set because enabling the validator at 80B
  TP=4 hits a *separate*, still-open CCL collective deadlock (works at
  TP=1 debug; deadlocks at TP=4/62N). That is tracked independently and
  was deliberately sidestepped here so the batch-size question could be
  answered in isolation.
- Native `submit_agpt_80b_autoretry.sh` worked end to end: 62 active /
  6 spare split, `--np=744`, yeet, attempt 1 reached training with no
  bad-node swaps; the run ended by walltime cut at step 46 (step 47 would
  have needed ~305 s more, past the 4h cap).
