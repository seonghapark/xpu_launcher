## Node Constraint

These nodes (`x4216c5s*`) could not run 80B at TP=2 due to insufficient
free XPU memory (OOM at model init, even without compile). The prior
benchmark (2026-03-30, nodes `x1921c1s*`) ran TP=2 at 93.49% utilization.
All experiments here use TP=3 or TP=6 with the `80B_alt` variant
(ffn_hidden=25596, divisible by 3 and 6).

## Analysis

### Compile impact

| Variant | TP | No Compile | Compile | Speedup | Memory Delta |
|---------|-----|-----------|---------|---------|-------------|
| 80B_alt | 3  | 20 TPS    | 23 TPS  | +15%    | -0.8 GiB    |
| 80B_alt | 6  | 41 TPS    | 45 TPS  | +10%    | -4.6 GiB    |
| 80B_deep_alt | 6 | 40 TPS | 44 TPS | +10%   | +0.4 GiB    |

torch.compile provides a consistent 10-15% throughput improvement.
At TP=6 with 80B_alt, compile also *reduces* memory by 4.6 GiB (operator
fusion eliminates intermediate tensors).

### TP scaling

| TP | TPS (compiled) | TFLOPS | MFU  | Memory    |
|----|---------------|--------|------|-----------|
| 3  | 23            | 12.46  | 4.18% | 51.6 GiB |
| 6  | 45            | 24.53  | 8.23% | 39.5 GiB |

TP=6 is 2x faster than TP=3 despite 2x more AllReduce overhead per step.
The communication cost is offset by much smaller per-rank tensors fitting
better in on-chip memory.

### Model variant comparison (TP=6, compiled)

| Variant      | Dim   | Layers | TPS | TFLOPS | MFU   | Memory |
|-------------|-------|--------|-----|--------|-------|--------|
| 80B_alt     | 9216  | 84     | 45  | 24.53  | 8.23% | 39.5 GiB |
| 80B_deep_alt| 7680  | 96     | 44  | 23.91  | 8.02% | 41.6 GiB |

The wider variant (80B_alt) is slightly faster and uses less memory than
the deeper variant (80B_deep_alt). More layers means more sequential
overhead per step, and the narrower hidden dim doesn't compensate.

### Async TP

Enabling `enable_async_tensor_parallel` with TP=6 + compile produced no
throughput gain (45 TPS with and without). At TP=6, per-rank tensors are
small enough that AllReduce communication is not a bottleneck.

### FSDP reshard policy

`fsdp_reshard_after_forward=never` OOMed at 56.07 GiB (87.6%) on step 2.
Keeping weights unsharded after forward adds ~16 GiB over the default
reshard policy, which is too much for these memory-constrained nodes.

### Comparison to prior benchmark (2026-03-30)

| Config   | TP | Prior TPS | Current TPS | Notes |
|----------|-----|----------|------------|-------|
| 80B      | 2   | 85       | OOM        | node memory issue |
| 80B_alt  | 3   | 23       | 23 (compile) | matches with compile |
| 80B_alt  | 6   | 43       | 45 (compile) | +5% with compile |

## Conclusions

1. **Best config on memory-constrained nodes:** 80B_alt TP=6 + compile (45 TPS, 8.23% MFU)
2. **torch.compile is always beneficial:** +10-15% TPS, often reduces memory
3. **async TP and reshard=never don't help** at TP=6 on these nodes
4. **80B_alt > 80B_deep_alt** for throughput at equal TP
5. **TP=2 requires nodes with >60 GiB free** XPU memory (93.5% of 64 GiB)
