# 80B GBS=2976 1024N-batch simulation (Sunspot, 2026-06-26)

Third rung of the 80B global-batch simulation campaign: pushes the
TP=4/LBS=1/bf16 stable corner to **8x the validated global batch**
(GBS=372 -> 2976) via GAS=16, simulating the global batch an Aurora
**1024N** production run would see -- while staying inside the NaN-free
`dp_degree <= 186` corner.

**Result: clean success.** 34/34 steps before the 6h walltime cut, zero
NaN, loss 12.92 -> 9.84. The corner holds at 8x batch.

See [`2026-06-25-80b-gbs1488-512N-sim.md`](2026-06-25-80b-gbs1488-512N-sim.md)
for the method (why GAS not nodes), the dp_degree<=186 derivation, and
the full root-cause of the campaign's blendcorpus-barrier arc -- all
shared with this run.

## Config

- Job `12469626`, Sunspot `workq`, 62 active + 4 spare (select=66),
  `scripts/submit_agpt_80b_autoretry.sh` (native `ezpz launch
  --auto-retry`), `MAX_FAILOVER_RETRIES=3`.
- `agpt_80b` (complex RoPE), TP=4, LBS=1, **GAS=16 -> GBS=2976**,
  dp_degree=186, AdamW LR=1e-6, bf16-compute / fp32-master, AC=full,
  compile=OFF, `VALIDATOR_ENABLE=0`.
- `--np=744`, ~610 s/step (2x the GBS=1488 run's ~305 s, as expected for
  2x microbatches), 6h walltime cap.
- Data: `data-lists/sunspot/books.txt` (blendcorpus). The index cache was
  built **cold at 744 ranks** on this run's first attempt and loaded
  clean (rank-0 build 0.008 s, all ranks loaded) -- no build-then-load
  race at this index size. (At the larger GBS=5952 the race does fire;
  see the GAS=32 run.)

## Aurora-1024N equivalence

| Quantity | This run | Aurora 1024N (TP=4, GAS=1) |
|---|---|---|
| dp_degree | 186 | 3072 (would NaN -- 16x over the ceiling) |
| GAS | 16 | 1 |
| **GBS** | **2976** | **3072** (~3% larger) |

GBS=2976 is within ~3% of the Aurora 1024N global batch (3072), so the
optimizer sees a representative batch while dp_degree stays pinned at the
validated 186. This is a *batch-size* simulation, not a node-count one --
it does **not** exercise dp_degree>186 (the real 1024N grad regime) or
the >512N init path.

```
step   1  loss 12.92  grad_norm  7.97
step   5  loss 12.80  grad_norm  8.01
step  10  loss 12.37  grad_norm  8.34
step  15  loss 11.67  grad_norm  8.12

step  23  loss 10.80  grad_norm 21.52   <- grad_norm peak, recovered
step  25  loss 10.61  grad_norm 17.11
step  30  loss 10.14  grad_norm  9.40
step  34  loss  9.84  grad_norm  9.31   <- final (walltime cut)
```

- **Loss:** 12.92 -> 9.84 (-3.1 nats over 34 steps), monotone modulo
  small noise.
- **grad_norm:** bounded throughout. The step-22-27 transient peaked at
  21.5 (step 23) and recovered to ~9.3 -- the *same* transient shape and
  magnitude as the GBS=1488 run (peak 22.4 @ step 23), not a blowup. No
  NaN one step before loss (the grad-path failure signature). Verified
  **zero NaN/inf** across all 34 steps.
- **MFU:** steady ~9.85% (the documented TP=4 cost, GAS-independent);
  memory flat 32% (20.5 GiB/tile).

Striking: GBS=2976 at step 34 (9.84) is **identical** to GBS=1488 at
step 34 (9.84) and tracks the GBS=372 curve -- in this early regime the
loss-vs-step curve is nearly batch-size-invariant, while each GBS=2976
step consumes 2x the tokens of GBS=1488 (and 8x of GBS=372). The point
is stability, not a per-step race: **8x GBS, still zero NaN, same smooth
descent.**

## Significance

The TP=4/LBS=1/bf16 corner now holds at GBS=372 (100 steps), 1488 (4x),
and **2976 (8x)** -- spanning the native, 512N-equivalent, and
1024N-equivalent global batches, all NaN-free on the safe side of the
dp_degree<=186 ceiling. The corner's stability is a property of the
(TP=4, LBS=1, dp<=186) regime, independent of batch size.

Still **not** established by these batch sims: survival of
`dp_degree > 186` (the actual 1024N+ regime, where dp itself is the
trigger) or the >512N distributed-init path. Those need a node-count
study -- the dp-degree cliff bisect (n64/n88/n108 -> dp 192/264/324),
queued.
