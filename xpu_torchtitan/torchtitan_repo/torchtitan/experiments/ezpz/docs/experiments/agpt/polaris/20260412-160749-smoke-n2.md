## Notes

- **7B** fits comfortably at 31% memory, leaving headroom for larger batch sizes.
- **8B** uses `vocab_size=128256` (Llama 3 architecture) which requires a Llama 3
  tokenizer not available on this system. CUDA assert on embedding index out of bounds.
- **20B** runs at 89% memory utilization with heavy CUDA allocation retries.
  Memory-bound at ~10.7 TFLOPS (3.4% MFU). Would benefit from TP=2 or more nodes.
- **50B** OOM with TP=2, FSDP=4, LBS=1, seq=4096. PyTorch allocates ~36 GiB/GPU.
  Needs 4+ nodes or A100-80GB GPUs.
- **80B** OOM with TP=4, FSDP=2, LBS=1, seq=4096. PyTorch allocates ~38.2 GiB/GPU.
  Needs 4+ nodes or A100-80GB GPUs.

## Known Issues

### torch.compile + `sdpa_kernel(set_priority=True)` on Polaris (FIXED)

Initial runs crashed with `RuntimeError('Invalid backend')` during `torch.compile`
tracing of `F.scaled_dot_product_attention` inside a `sdpa_kernel(..., set_priority=True)`
context manager.

**Root cause:** `torch._dynamo` bug in PyTorch 2.11 — `SDPAKernelVariable.enter()`
in `ctx_manager.py` creates FX graph nodes that pass proxy objects to `int()` when
`set_priority=True`, producing invalid backend IDs for `_set_sdp_priority_order()`.

**Fix:** `EzpzScaledDotProductAttention` subclass overrides `forward()` to use
`sdpa_kernel(self.sdpa_backends)` without `set_priority=True`. Device-aware
`_default_inner_attention()` selects the right subclass (XPU vs CUDA).

### Blendcorpus data cache race condition

When using a `seq_len` or `global_batch_size` that hasn't been cached before,
rank 0 builds the cache files while other ranks race to read them, causing
`FileNotFoundError` or `EOFError`. Workaround: run once to build cache (it will
crash on non-zero ranks), then retry — the cache files persist on disk.
