## Summary

Job 8479579 (canonical 20B 512N chain continuation, resumed from
step-800) trained for **3 steps** (801 → 803, ~3 min wall) then
**hung silently for ~5 hours** before being killed manually with
`qdel`. The job remained in `R` state the entire time, with W&B
heartbeat telemetry from rank-0 still firing every 15s, but **no new
training metrics** were logged after step 803.

This is a **new failure mode** distinct from anything our
[bad-node failover wrapper](../../../guides/bad-node-failover.md)
currently handles — there's no exit, no crash, no traceback, no
signal-N death. The job just stops making progress. Without manual
observation it would have eaten the full 12h walltime allocation
(512 nodes × 12h = 6,144 node-hours wasted).

## Diagnostic notes

**What was alive:**
- rank-0 process was still doing W&B `filestream: sending request` →
  `request sent: 200 OK` every 15s until kill, with `events_offset`
  advancing by 1 each round. So `wandb-core` was actively talking to
  the W&B server.
- PBS reported the job in `R` state; node session ID present;
  walltime accumulating normally.

**What was dead:**
- `agpt-20b-n512-v2-chain2.o8479579` stdout file: **last write at
  13:30:40** (165KB, never grew after that).
- `outputs/tb/.../files/output.log`: same — last write 13:30:45.
- No new ckpts saved since step-800 (the resume point). The next
  expected save (step-900 at 100-step interval) never happened.

**Hypotheses (not yet verified):**
1. **Some rank deadlocked in a collective.** rank-0 still alive
   (W&B telemetry working) but most of its threads waiting for a
   gather/all-reduce that never completes because some other rank
   on a bad node is unresponsive. Training-step `print` writes go
   through a `dist.barrier()` in `EzpzValidator`/`Trainer`'s logger
   path, so rank-0 won't print step 804 until the bad rank checks in.
   — Most likely. Matches the symptom of "W&B heartbeat alive,
   training metrics dead".
2. **Stdout buffering pathology.** Less likely — the W&B file would
   be flushing to its own buffer. But possible if `tee` or PALS is
   eating the buffer.
3. **Genuine progress at 100,000+ s/step.** No — memory usage on
   the W&B side suggests no new optimizer steps, and 5h is way past
   any reasonable per-step bound for this config.

## Implications for the failover wrapper

`failover_lib.sh` currently retries on **non-zero exit**, scraping
the log for known crash patterns. It cannot detect the hang
scenario, because the job never exits. To handle this we'd need:

- A **no-progress watchdog** — periodically check the log file's
  mtime (or grep for the latest `step: N` line); if no new step in
  N minutes (e.g. 30 min for 20B at 512N where steps are ~45s
  uncontested), assume hung and `qdel` from inside the job, then
  retry with a swap-in.
- Possibly a separate background process that monitors PBS_NODEFILE
  reachability (e.g. `pdsh -f 64 -w ^$PBS_NODEFILE date` every 5
  min) — if any node stops responding, that's the bad one to swap.

Both add complexity. Filed as a follow-up; not blocking the v1
failover wrapper.
