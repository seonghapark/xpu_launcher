## Understanding MFU for MoE Models

### How MFU is computed

The reported MFU uses **active parameters** -- the parameters that actually
participate in each forward pass -- not the total (sparse) parameter count.
For a MoE layer with `E` experts and `top_k` routing:

```
active_expert_params = (top_k / E) * total_expert_params
```

The FLOP estimate follows the standard transformer formula, substituting
active parameters for the MoE layers:

```
flops_per_token = 6 * (dense_params - embedding_params + sparse_active_params)
               + 6 * n_layers * n_heads * head_dim * seq_len

MFU = flops_per_token * tokens_per_second / peak_device_flops
```

Where `peak_device_flops = 2.982e+14` (298.2 TFLOPS) for Intel Max 1550.

This is the correct formulation: since only `top_k` out of `E` experts run
per token, counting all expert parameters would overstate the actual compute.
The reported MFU reflects real hardware utilization relative to peak.

### Dense-equivalent MFU

For comparison with dense models, one can compute a "dense-equivalent MFU"
using total parameters. This shows what MFU would be if every expert were
activated per token:

| Config      | Active MFU | Dense-eq MFU | Ratio (active/total) |
|-------------|-----------|-------------|---------------------|
| 500M        | 8.33%     | 4.61%       | 55.4%               |
| 2B          | 7.18%     | 2.18%       | 30.3%               |
| 4B          | 3.60%     | 1.00%       | 27.9%               |
| 7B          | 3.28%     | 0.68%       | 20.8%               |
| 10B_2B_sdpa | 2.82%     | 0.60%       | 21.1%               |

Dense-equivalent MFU = Active MFU * (active_params / total_params). As expert
count grows, a smaller fraction of parameters is active per token, widening
the gap between active and dense-equivalent MFU.

## Known Issues

### Activation checkpointing + MoE routing (7B, 10B_2B_sdpa)

The `moe_7b` config fails with `activation_checkpoint.mode=full`:

```
torch.utils.checkpoint.CheckpointError: Recomputed values for the following
tensors have different metadata than during the forward pass.
tensor at position 98:
  saved metadata: {'shape': torch.Size([1826, 2048]), ...}
  recomputed metadata: {'shape': torch.Size([1827, 2048]), ...}
```

**Root cause:** MoE routing is non-deterministic across forward and
recomputation passes. The router's top-k selection dispatches a different
number of tokens to each expert on recompute, producing tensors with
different shapes (+/- 1 token per expert).

**Affected configs:** `moe_7b` (confirmed), `moe_10b_2b_sdpa` (precautionary).
Smaller configs (500M, 2B, 4B) did not exhibit this in 50-step tests.

**Workaround:** `--activation_checkpoint.mode none`. Increases memory
(~3.8 GiB -> ~20-23 GiB per device) but avoids the error.

**Potential fixes:**
- Deterministic routing (seed the router during AC recomputation)
- `preserve_rng_state=True` in `torch.utils.checkpoint`
- Custom AC wrapper that saves/restores router decisions
- Upstream fix for dynamic-shape ops in checkpoint recomputation

### XPU autocast warnings

All configs emit warnings about `torch.autocast` not supporting `float32`
on XPU. Non-fatal -- the SDPA configs avoid the critical path where
FlexAttention would trigger fp32 autocast in the MoE router.
