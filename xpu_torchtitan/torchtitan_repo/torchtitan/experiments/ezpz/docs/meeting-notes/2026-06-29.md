## 2. 80B production launch — needs a team decision on optimizer

First real 80B v2 production dispatches. Queued, start post-PM.

| Bracket | jobs (head/cont) | active+spare | GBS | ~steps |
|---|---|---|---|---|
| 512N | 8574385 / 8574388 | 510 + 6 | 6120 | 93,223 |
| 1024N | 8574386 / 8574389 | 1022 + 14 | 6132 | 93,041 |
| 2048N | 8574387 / 8574390 | 2046 + 26 | 6138 | 92,950 |

Common config: **SophiaG LR=1e-6**, **constant LR after warmup**
(`decay_ratio=0`, warmup 4650 = 5%), TP=4 / LBS=1, compile OFF, AC=full,
validator ON (95/5 split, freq=500). GBS held ~6144 across brackets (via GAS)
so the LR stays calibrated; spares ~1.3% of active (scale with N).

**Decision 1 — optimizer (SophiaG vs mano).** Per the 2026-06-27
production-batch LR-finder (GBS=6144):
- **AdamW is on a NaN cliff** — usable LR ceiling ~7e-7, NaN onset 1.36e-6, so
  the old "LR=1e-6" default diverges. AdamW is the worst of the three.
- **mano** is the *safest*: clean broad U-curve, ~20x LR headroom, suggested
  **~3e-6**.
- **sophiag** has the *lowest* min loss (12.60 @ 2.5e-6) but a **narrow band**
  (blow-up onset ~4.6e-6); conservative rec **~1e-6**.
- **We launched SophiaG @ 1e-6.** Question for the team: keep SophiaG, or switch
  the 80B base to **mano @ 3e-6** for the wider stability margin on a long
  unattended run? (Easy to switch before they start.)

**Decision 2 — scale risk.** No v2 run has succeeded above ~512N. 1024N
(12,288 ranks) is documented to crash at init (`set_determinism`); 2048N
(24,576 ranks, dp_degree~6138) is 2x that, untested. The 512N bracket is the
safety net; submitting all three simultaneously *is* the scaling experiment.
Set expectations: the 1024/2048N brackets may crash at startup — that's data,
not a regression.

**Decision 3 — constant LR is deliberate (CPT).** No decay after warmup, by
design, so we can continue pre-training past the nominal budget. Flag so nobody
"fixes" it back to a decay schedule.

(A 4N pre-check confirmed the SophiaG/constant-LR config wires through correctly
and trains cleanly before we committed the big allocations.)

## 3. Infra fixes this week (all landed + pushed)

- **blendcorpus cold-cache index race — FIXED at source.** Was blocking any
  fresh-`CKPT_DIR` 80B run: at TP>1 the non-rank-0 readers raced rank-0's index
  write (EOFError/mmap on ~75% of ranks). Fixed in `saforem2/blendcorpus` via
  atomic writes + poll (`041d015f`) plus a TOCTOU follow-up (`1f7e9c0`).
  Confirmed end-to-end (cold 4N TP=4 80B trains, 0 errors). **80B no longer
  needs a manual cache prewarm.**
- **Validator at 80B TP=4 — the "CCL deadlock" was a phantom.** It conflated 3
  unrelated bugs (cold-cache mmap race, a training-side barrier stall, a
  `loss_fn` tuple-unpack crash), all now fixed. Validation **confirmed working**
  at TP=4 (job 12469784). `VALIDATOR_ENABLE=1` is safe again; 95/5 split is the
  default — hence validation is ON for the 80B runs.
- **Checkpoint-resume incident (caused + recovered).** A clone `git pull`
  advanced the production clones past an optimizer state-dict format migration
  (#3623/#3269, nested->flat), breaking DCP resume. Recovered by pinning the
  clones pre-#3623; resume verified on hardware. The clones stay pinned — a
  nested->flat migration shim is hard/risky and unnecessary (chains resume fine
  pinned). **Takeaway: don't blanket-`git pull` a production clone; cp/checkout
  only the intended infra files.**
- **Walltime-aware checkpointing** added to the ezpz trainer (force a final
  ckpt before walltime SIGKILL) + a job-absolute-deadline fix so it survives
  failover retries.
