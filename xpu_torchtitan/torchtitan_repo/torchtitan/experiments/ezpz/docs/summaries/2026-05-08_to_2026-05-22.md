## 1. Upstream PR filed: xccl `_set_pg_timeout` dispatch (in flight)

The largest single thread of work this period.

**The bug.** `torch.distributed.distributed_c10d._set_pg_timeout` has
device branches for cpu/gloo and cuda/nccl/torchcomms — but **no
xpu/xccl branch**. On every Intel XPU run, calling it (which torchtitan
does every step via `CommConfig.train_timeout_seconds`) silently no-ops
and emits the `"Set timeout is now only supported for either nccl or
gloo."` warning. The diagnostic gap behind the 2026-05-20
`moe_debugmodel_ep` step-41 hang: 100 s configured, 985 s silence
observed, no abort.

**Local workaround landed in torchtitan** (commit
[22847fcb3](https://github.com/saforem2/torchtitan/commit/22847fcb3)):
`_set_pg_timeouts_xpu_aware` in `experiments/ezpz/trainer.py` walks
each PG and calls `ProcessGroupXCCL.set_timeout` directly. You'll see
the `Applied train timeout 0:01:40 to N xccl ProcessGroup(s) (upstream
_set_pg_timeout has no xpu branch).` log line on every training run
now — that's the workaround firing.

**Empirical verification + writeup**:

- [`verify_pr1_dispatch.py`](../upstream-issues/verify_pr1_dispatch.py) —
  standalone verifier with a monkey-patched class-method spy that
  detects (a) whether the warning fires and (b) whether
  `ProcessGroupXCCL.set_timeout` is actually called. Commit
  [e5eb469df](https://github.com/saforem2/torchtitan/commit/e5eb469df).
- [`VERIFY_pr1_dispatch_results.md`](../upstream-issues/VERIFY_pr1_dispatch_results.md) —

- Side finding: contrary to the pessimistic line in
  [`PLAN_xccl_timeout_upstream_pr.md`](../upstream-issues/PLAN_xccl_timeout_upstream_pr.md),
  xccl's C++ `set_timeout` **does** propagate the value into
  `backend.options._timeout`. Only *enforcement* (watchdog + abort) is
  missing — PR 2's scope, not PR 1's.
