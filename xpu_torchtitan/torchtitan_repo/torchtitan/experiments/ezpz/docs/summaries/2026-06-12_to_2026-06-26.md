## 1. 80B NaN root cause + the TP=4 stable corner (headline)

The multi-week 80B NaN saga resolved. A controlled multi-node sweep
(LR=1e-6, all at 62N) mapped the grad_norm-first NaN to **two
independent triggers**, both in the gradient path -- it is *not* a raw
global-batch threshold. Full matrix + perf table:
[`production/agpt/80b/README.md`](../production/agpt/80b/README.md);
the reconciled n32 factorial:
[`experiments/agpt/aurora/20260611-80b-n32-nan-diagnosis.md`](../experiments/agpt/aurora/20260611-80b-n32-nan-diagnosis.md).

| Job | TP | LBS | GAS | dp_degree | GBS | Result |
|---|---|---|---|---|---|---|
| 12469486 | 2 | 1 | 1 | 168 | 168 | clean -> 10.38 |
| 12469492 | 2 | 1 | 1 | 372 | 372 | **NaN @ step 3** |
| 12469494 | 4 | 1 | 2 | 186 | 372 | clean -> 10.31 |
| 12469495 | 4 | 1 | 1 | 186 | 186 | clean |
| 12469499 | 4 | **2** | 1 | 186 | 372 | **NaN @ step 4** |

- **Trigger 1: large `dp_degree`** (= NGPUS/TP). GBS=372 is clean at
  dp=186 (12469494) but NaNs at dp=372 (12469492).
- **Trigger 2: `LBS > 1`** -- 12469499 NaNs at the *same* dp=186 as the
  clean runs, differing only by LBS=2 vs LBS=1+GAS=2.
- The safe corner is **LBS=1 AND dp_degree <= ~186**; reach a target GBS
  by adding **GAS** (sequential microbatches), which scales GBS without
  touching dp_degree. TP=4 helps only because it halves dp_degree at
  fixed NGPUS -- it is not a TP fix per se.
- **Stability CONFIRMED 4/4 clean** (12469494/509/510/511; three at
  identical loss 9.69-9.70) -- not a nondeterministic knife-edge.
  ([`764352c15`](https://github.com/saforem2/torchtitan/commit/764352c15),
  [`da63b4b7d`](https://github.com/saforem2/torchtitan/commit/da63b4b7d),
  [`588227b68`](https://github.com/saforem2/torchtitan/commit/588227b68)).
- **New production recommendation: TP=4 / LBS=1 / bf16 / GAS-to-GBS**,
  ~9.85% MFU (~half the TP=2 baseline; the cost is TP=4 comm, confirmed
  GAS-independent). Supersedes the n32 factorial's fp32-acts default
  (~3-5x slower) -- that factorial never tried TP=4/LBS=1 with GAS.
- Added a **batch-size ramp** (`FaultTolerantTrainer.batch_ramp_steps`,
  [`09f2d243b`](https://github.com/saforem2/torchtitan/commit/09f2d243b))
  that ramps GAS like LR warmup -- mitigates the dp-degree onset (not the
  LBS trigger).
- The underlying TP=2 / LBS>1 grad-path overflow remains an open,
  upstream-worthy bug; two cheap 62N reproducers now exist.

## 6. blendcorpus index-cache race + the barrier lesson

The blendcorpus index cache (keyed by `md5(corpus + num_samples + ...)`,
where `num_samples = GBS * train_iters`) exposed a **build-then-load
race** at TP>1: rank-0 builds, TP-coord!=0 ranks `np.load` mid-write
(`EOFError` / `mmap length > file size`).

- **Three correct global barriers** added next to pre-existing all-rank
  collectives (`_cache_indices`, `build_corpus_datasets`,
  `blendable_dataset.py`; blendcorpus `debfff5`).
- **One wrong barrier** in `_build_index_mappings` (`c7eb628`) -- that
  function is called a *data-dependent* number of times (per corpus x per
  split, branch-gated), so ranks reached it a mismatched number of times
  -> oneCCL `allreduce_scaleout` participation deadlock. **Reverted
  (`74b09fd`)**; a NOTE documents why no barrier belongs there.
- Operational mitigation: `scripts/prewarm_blendcorpus_cache.sh`
  ([`8352b9460`](https://github.com/saforem2/torchtitan/commit/8352b9460))
  + the per-run `--validator.dataloader.data-cache-path`
  ([`f1e269661`](https://github.com/saforem2/torchtitan/commit/f1e269661)).
- **Empirically (2026-06-26)**: cold-build at 744 ranks *succeeds* for
  moderate indices (GBS=2976) but the race *does* fire for large ones
  (GBS=5952) -- and **auto-retry self-heals it**: attempt 1 finishes the
  write, attempt 2 loads warm, at the cost of one spare node.
- Lesson (systematic-debugging): a barrier is only safe where every rank
  provably reaches it the same number of times; and read *all* the
  failure logs before naming a single root cause (there were two).

## 11. Aurora production ops -- 512N starvation, sneak jobs, umbrella, walltime ckpt (2026-06-26)

A focused Aurora session attacking the chronic 512N queue starvation. The
512N canonical chains (2B + 20B) had sat in `small` ~21 days
(`8521631`/`8521632`, eligible since 2026-06-07, `est_start = NONE`): a
522-node scatter request rarely wins a slot against the crowd.

- **Short "sneak" jobs DO land** (updating the prior "do not resubmit"
  guidance in [`queue-wait-analysis.md`](../production/queue-wait-analysis.md)).
  2h-walltime 512N jobs are far more backfill-eligible than the 12h heads
  (`backfill_max=50` active). Both landed 2026-06-26 (`8564220` 2B,
  `8564221` 20B); the 20B trained step 4400 -> 4415+ -- first 512N
  progress in 3 weeks. They resume the SAME canonical ckpt dir (CKPT_DIR
  is model/node/gbs-derived), so they advance the chain, not a fork.
- **Two new failure modes** found + recorded:
  - **CCL/PMI KVS-timeout** segfault in `libccl` during collective init at
    6144 ranks (killed the first 2B sneak `8564220`; failover spare-swaps
    cannot fix a system-wide KVS timeout -- same class as the pals-RPC
    transient; resubmit). [[project_ccl_kvs_timeout_init_crash]]
  - **Short jobs save nothing** at the default `CKPT_INTERVAL=100`: the 20B
    sneak at ~48s/step reaches only ~step 4490 in its 2h window, missing
    the step-4500 save by ~9 min. [[feedback_short_jobs_need_short_ckpt_interval]]
- **Multi-chain "umbrella" job** ([`b66ba7235`](https://github.com/saforem2/torchtitan/commit/b66ba7235),
  `submit_agpt_multi_aurora_venv_failover.sh`): packs all 4 canonical
  chains (2B/20B x 512N/256N = 1536 train nodes) into ONE allocation that
  routes to the empty `medium` queue (1025-1999 band) instead of the
  jammed `large` or starved `small`. It slices PBS_NODEFILE into 4
  disjoint hostfiles and runs the existing child submit scripts as 4
  concurrent isolated subprocesses (per-trainer FAILOVER_LOG_DIR /
  MASTER_PORT / CKPT_DIR / QUEUE_WAIT_CSV / PBS_O_WORKDIR). DRY_RUN +
  MULTI_PROFILE=tiny test paths. **Tiny-scale smoke (`8566938`/`8567189`)
  caught a real bug**: `ezpz yeet`'s local-copy always runs on the shared
  mom node at a fixed `/tmp` dst, so 4 concurrent child yeets corrupt each
  other (rc=127). Fixed by pre-staging each distinct venv ONCE, serially,
  to a per-model `/tmp/.venv-<model>` dst, with children getting
  `SKIP_YEET=1` + `VENV_DST` (both default to current behavior).
  [[project_yeet_single_job_per_alloc]]
- **Walltime-aware checkpointing** ([`3d9044993`](https://github.com/saforem2/torchtitan/commit/3d9044993)):
  `FaultTolerantTrainer.train()` now watches a monotonic clock and forces
  a final checkpoint once elapsed reaches `walltime_seconds - margin`
  (reusing the `last_step` interval-bypass + `maybe_wait_for_saving()` to
  flush async), guaranteeing a save before walltime regardless of step
  rate. `walltime_seconds=0` (default) disables it; the failover submit
  scripts export REMAINING walltime (new `failover_remaining_walltime()`
  helper) via `--envall`. The durable fix for the "short jobs save
  nothing" mode above.
- **Maintenance window**: full-machine PM reservation **Mon 2026-06-29
  06:00 -> Wed 2026-07-01 03:30 UTC**. Short 2h jobs stay launchable ~10h
  longer into the pre-PM drain than the 12h heads; the post-PM flood is
  the best big-job landing window (the umbrella's intended slot).
